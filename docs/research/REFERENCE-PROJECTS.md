# 参考项目、要求映射与使用边界

更新时间：2026-08-31

## 使用原则

参考项目用来缩短产品和工程探索，不用来拼接功能清单。每个候选能力只有同时满足以下条件才进入 PLDR：

1. 解决 `../product/FUNCTIONAL-PERFORMANCE-REQUIREMENTS.md` 中已经存在的用户问题；
2. 不破坏来源—文档—快照—主张—证据—研判链路和人工确认边界；
3. 有明确阶段、退出条件和可证伪验收；
4. 代码、服务、数据、商标和部署方式经过单独许可证与条款复核；
5. 引入成本低于独立实现或薄适配的长期成本。

“借鉴”默认表示研究交互和架构模式，不表示复制源码、兼容其全部接口或接受其技术栈。当前 PLDR 前后端为独立实现；P0 实际采用自有的 World Monitor 风格兼容壳，没有导入完整 World Monitor 上游源码。

## 当前吸收结论

P1 不再以“再接入多少开源项目”衡量进度，而以以下缺口为准：

1. 冻结首个真实专题包和 30–50 个来源；
2. 将固定监测、动态发现和主动导入收敛为清楚的今日工作流；
3. 完成通用 API、必要的受控浏览器来源和 RSS 原文追抓；
4. 完成 72 小时运行、安全收敛、性能基准和模型成本台账；
5. 用真实任务证明已确认结论能够完整回到证据。

只有当上述缺口出现自研成本、可靠性或合规瓶颈时，才从本表选择上游项目进入独立 ADR 和试验。正式采用时必须记录仓库 URL、固定 commit、`LICENSE`、`NOTICE`、部署拓扑、数据条款、维护责任和退出方案。
