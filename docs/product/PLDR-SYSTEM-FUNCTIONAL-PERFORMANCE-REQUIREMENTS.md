# PLDR 系统功能与性能要求

**版本：** 1.0
**日期：** 2026-08-31
**用途：** 明确系统建设、交付和验收的主要技术要求。

## 1. 建设目标

PLDR 应面向公开信息收集、证据整理和专题研判，形成统一的“输入—处理—呈现”工作流程：

```text
输入：专题目标、关键词、网页/RSS、粘贴文本、本地文件
  ↓
处理：采集与快照、去重、AI 整理、人工确认
  ↓
呈现：中文结论、关键发现、时间线、参与方、信息缺口、专题报告
```

系统应坚持证据优先和受控 AI。搜索结果、网页摘要及 AI 生成内容只能作为候选；未经人工确认的内容不得进入正式专题成果和报告。正式结论必须能够回溯至证据片段、固定快照、原始材料和信息来源。

## 2. 功能要求

| 编号 | 要求 |
| --- | --- |
| F-01 | 系统应采用浏览器/服务器架构，用户通过浏览器完成专题创建、资料处理和成果查看。 |
| F-02 | 用户应能填写专题名称、核心问题、可选的事件时间范围，并选择一次性研究或持续关注。 |
| F-03 | 创建专题时应能同时提交关键词、网页/RSS、粘贴文本和本地文件，无需先建立空专题再重复录入。 |
| F-04 | 系统应支持关键词或自然语言搜索公开新闻及网页，显示标题、来源、摘要、时间和链接，并支持分页、跨页选择、去重及查询历史；应按专题词对标题和摘要进行可解释的相关性初筛，存疑或可能无关结果默认不得进入专题待处理，但仍可查看和人工选择。 |
| F-05 | 系统应支持固定网页和 RSS/Atom 周期采集，保存版本与差异，避免重复条目重复进入处理流程，并支持暂停、恢复和重试。 |
| F-06 | 系统应支持公共网页、粘贴文本及 TXT、Markdown、HTML、PDF 文件；应保存原始内容、提取文本、采集时间和内容哈希。 |
| F-07 | 系统应基于已保存原文生成候选事件、实体、主张、证据及关系；模型临时失败应自动退避重试，多次失败后允许人工重新分析，且不得造成原始材料丢失或产生伪成功候选。 |
| F-08 | 用户应能核对原文，对候选内容执行采用、修改后采用或不采用；正式写入前必须显示新建、修改或合并内容的预览。 |
| F-09 | 失败记录应说明阶段、原因、影响及建议操作，并支持重试或删除；单条失败不得影响同批其他资料。 |
| F-10 | 系统应建立“来源—材料—快照—事件/实体—主张—证据—研判—报告”关联链，主张和报告引用应可逐级回溯。 |
| F-11 | 专题首页应优先呈现当前结论、最新变化、关键发现与证据、事件时间线、关键参与方、信息缺口和报告历史。 |
| F-12 | 系统应提供事件时间线和地图视图；地图事件应能打开事件档案和证据，不得为缺少可靠坐标的数据伪造位置。 |
| F-13 | 系统应生成只包含已确认内容的中文冻结报告，记录生成时间并保留历史版本；后续数据不得改写既有报告。 |
| F-14 | 系统应显示来源健康状态、最近检查及成功时间、失败次数和原因；专题之间的数据应默认隔离，首页全部专题汇总与具体专题待处理队列必须明确区分。 |
| F-15 | 用户界面和正式成果应以中文呈现；外文材料应保留原文，不得以机器翻译内容替换原始证据。 |

## 3. 性能与质量要求

| 编号 | 指标要求 |
| --- | --- |
| P-01 | 本地只读 API 响应时间 P95 应不大于 500 ms。 |
| P-02 | 首页可交互时间应不大于 3 秒；专题列表及待处理列表加载时间应不大于 2 秒。 |
| P-03 | 专题成果首屏可用时间应不大于 3 秒；证据详情展开时间应不大于 1 秒。 |
| P-04 | 专题报告生成时间应不大于 10 秒。 |
| P-05 | 搜索请求总超时应不大于 12 秒；超时或上游错误时不得生成虚假结果。 |
| P-06 | 单次网页正文及单个上传文件的支持上限均应不低于 5 MB。 |
| P-07 | 单个 RSS 每次应能处理不少于 50 条记录。 |
| P-08 | 搜索结果应支持每页 10 或 20 条，单次查询累计不少于 100 条，单批选择处理不少于 100 条。 |
| P-09 | 系统应支持 30～50 个真实来源连续运行不少于 72 小时，并形成运行结果记录。 |
| P-10 | 服务重启后已入队任务丢失数量应为 0；过期任务应可恢复。 |
| P-11 | 已确认证据的原文命中率和已确认主张的证据回链率均应达到 100%。 |
| P-12 | 未确认内容进入正式成果的数量应为 0；重复确认产生的重复正式对象数量应为 0。 |
| P-13 | 单条资料处理失败对同批其他资料的影响数量应为 0；失败信息完整显示率应达到 100%。 |
| P-14 | 1440×900 桌面视口应能完成完整流程；390×844 窄屏视口应能完成核心流程且无横向溢出。 |

## 4. 安全与兼容要求

| 编号 | 要求 |
| --- | --- |
| S-01 | 服务端应支持 Ubuntu Linux 和银河麒麟 V10；客户端应支持 Windows 10/11 上的主流 Chromium 浏览器。 |
| S-02 | 系统应支持内网部署和受控公网访问；公网访问必须使用 HTTPS 和身份认证。 |
| S-03 | 搜索服务、AI 模型服务和数据存储应采用可替换的适配方式，不得将核心业务流程锁定于单一厂商。 |
| S-04 | 仅允许采集公共 HTTP/HTTPS 地址；必须拒绝私网、回环、链路本地、保留地址及内嵌凭据的 URL。 |
| S-05 | 每次 DNS 解析和每一跳重定向均必须重新校验目标地址；无法确认安全时必须停止访问。 |
| S-06 | 网络请求必须设置连接、读取、总超时及响应大小上限。 |
| S-07 | 账号、密码和服务密钥必须从受控配置或秘密存储读取，不得出现在前端、日志、报告或源代码中。 |
| S-08 | 正式写入、修改、不采用、删除、恢复及报告生成应保留操作时间、对象和结果记录；备份恢复后证据链和历史版本应保持可用。 |

## 5. 验收要求

1. **功能验收：** 使用真实样例走通“创建专题并提交资料—采集与快照—AI 生成候选—人工确认—专题成果—证据回溯—冻结报告”的完整流程。
2. **性能验收：** 在约定的服务器、客户端和网络环境中按实际业务数据测试；响应时间指标以不少于 20 次有效样本的 P95 结果为准。
3. **稳定性验收：** 使用 30～50 个真实来源连续运行不少于 72 小时，核对去重、失败隔离、重试、重启恢复及资源使用情况。
4. **安全验收：** 对未认证访问、私网地址、内嵌凭据、DNS 变化、多跳重定向、超时、超大响应和密钥泄露进行负向测试。
5. **质量验收：** 未确认内容进入正式成果、证据无法回到固定原文、队列重启后丢失或关键安全校验可被绕过，均判定对应要求未通过。
