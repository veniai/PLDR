## 实施结果

P0 已于 2026-08-26 形成可运行纵向切片。当前实现包含 16 个来源、48 份文档、8 个事件、24 条主张和 56 条证据，自动验收与交互验收均通过。

由于当前执行环境无法取得完整 World Monitor 源码归档，实际采用了 ADR-0004 预留的退出路径：保留 World Monitor 的地图优先、面板化、任务模式、来源状态和信息缺口设计，自行实现轻量兼容壳；PLDR FastAPI、SQLite 和证据对象保持独立。完整源码 checkout 可用后，通过 overlay 按接口移植，不影响后端与数据模型。

当前 P0 已实现 URL 和 RSS 导入、模型兼容接口、离线固定演示包、事件详情、证据高亮快照和 HTML 报告。实时连续监控、自动事件聚合和分析员人工合并界面仍属于 P1。

## 目标

P0 用一个小而真实的纵向切片证明五件事：

1. 信息能够从公开来源进入系统，并显示抓取时间和来源状态。
2. 多篇重复或相关材料能够聚合到一个事件。
3. 事件中的关键主张能够展开到原文证据片段。
4. 文档数量与独立来源数量能够分开显示，并能看到来源差异。
5. 用户能够从选定事件和证据生成一份带引用的报告预览。

P0 不能退化成静态图片，也不追求完整生产系统。采用薄后端的真实纵向切片，保留 P1 可复用的对象和接口。

## 演示范围

一个公开、持续更新、具有地理和多来源特征的专题。10 至 20 个稳定来源，以 RSS、公开机构网站和普通新闻网页为主。30 至 60 篇文档，聚成 6 至 10 个事件。中文和英文优先，可加入一种当地语种作为跨语言展示。实时数据与缓存数据同时存在，并在界面中明确标记。

## P0 页面

### 1. 态势首页

顶部显示专题、时间范围、最后更新时间、来源健康和生成报告入口。主区域提供地图与时间线。地图只展示具有可靠地点的事件，没有地点的事件进入时间线和列表。右侧事件流显示标题、时间、地点、重要性、文档数量、独立来源数量、关键实体和待核实标记。

### 2. 事件详情

显示事件摘要、发生时间、地点、参与实体、演变时间线、相关文档和来源。显示主要主张、支持证据、冲突证据和待核实问题。文档数量与独立来源数量分开，转载或共同上游归入同一独立来源组。

### 3. 证据抽屉

点击主张后打开原文片段，突出显示证据句，展示标题、来源、发布时间、抓取时间、原文 URL、正文哈希和实时或缓存标签。证据片段必须是文档正文的真实子串。模型给出的引用在写入前进行程序校验，找不到原文时不得作为证据展示。

### 4. 报告预览

用户选择事件后生成 HTML 报告。报告包含执行摘要、事件时间线、主要主张、来源差异、信息缺口和引用。P0 只做 HTML 预览，PDF 延后到 P1。

### 5. 来源状态

展示来源名称、类型、最后成功时间、响应状态和最近错误。P0 不做完整来源管理后台。

## 最小对象

Source：来源名称、入口、语言、国家、类型、状态、最后成功时间。

Document：规范 URL、标题、发布时间、正文、语言、内容哈希、抓取时间、来源。

Event：标题、摘要、时间、地点、状态、重要性、文档数、独立来源数。

Entity：名称、类型、别名。

Claim：主张文本、状态、置信度、机器或人工来源。

Evidence：主张、文档、原文片段、起止位置。

EventDocument 和 EventEntity：事件与文档、实体的关联。

P0 不建立通用图数据库。关系图由上述关联临时生成。

## 数据进入与事件聚合

RSS 真实采集，普通网页使用轻量正文抽取。先做 URL 规范化和正文哈希，完全相同正文直接去重。候选事件按发布时间窗口、标题关键词和正文相似度分组。模型只承担事件标题规范化、摘要、实体地点和主张抽取。转载识别使用正文高相似度、发布时间和引用链接。

## 模型接口

业务代码只调用以下任务：`normalize_event_title`、`summarize_event`、`extract_entities_locations`、`extract_claims_evidence`、`draft_report`。

接口使用 OpenAI 兼容请求格式。通过环境变量配置 API Key、Base URL 和 Model Name。所有任务提供确定性降级。没有 API Key 或 API 失败时，系统仍能完整演示。

## 技术选择

前端：World Monitor 兼容改造壳，使用原生 JavaScript、SVG/网格态势图和面板化布局。完整上游源码可用后，再将 PLDR 组件迁入固定版本 World Monitor。

后端：FastAPI、Pydantic、SQLAlchemy。

存储：SQLite。P1 迁移 PostgreSQL。

采集：httpx、BeautifulSoup、lxml 和标准库 XML 解析。动态网页、浏览器集群和强反爬平台延后。

报告：Jinja2 HTML。

部署：FastAPI 同时提供静态 Dashboard 和 `/pldr-api/v1/*`，一条命令启动，也支持 Docker Compose。

## 72 小时节奏

第一天完成运行骨架、最小对象、SQLite、固定演示数据和首页；第二天完成事件、主张、证据、来源独立性和导入；第三天完成研判、报告、失败降级和验收。

## 验收门槛

1. 一条命令能够启动前后端。
2. 至少 10 个来源可展示，至少 30 篇文档进入系统，至少形成 6 个事件。
3. 展示的关键主张全部能够展开到真实原文片段。
4. 至少一个事件能够明显展示文档数与独立来源数的差异。
5. 报告中的引用能够回到事件、文档和证据。
6. 断网或模型 API 失败时，缓存数据仍能完成完整演示。
7. 三分钟内完成首页、事件、证据和报告四步演示。

## 明确排除

用户体系、复杂权限、多人审批、图数据库、向量数据库、OpenSearch、Kafka、Kubernetes、浏览器集群、强反爬社交平台、移动端、自动事实裁决、风险预测和群体模拟均不进入 P0。
