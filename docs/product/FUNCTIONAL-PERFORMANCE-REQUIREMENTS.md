# PLDR 功能与性能指标要求

版本：P1 基线 v0.1
更新时间：2026-08-31

## 1. 文档目的

本文档是 PLDR 当前阶段的功能、性能和验收基线，用来统一回答：

1. 分析员能够用 PLDR 完成什么工作；
2. 每项能力必须达到什么可观察结果；
3. 当前已经实现到哪里，距离阶段退出还缺什么；
4. 应使用什么样本、环境和证据判断“完成”。

`PRODUCT-VISION.md` 负责产品定位与不可破坏的原则，本文档负责可执行要求，`ROADMAP.md` 负责阶段顺序，各 P0/P1 切片文档负责具体契约和历史验收记录。任何功能不能仅因出现在界面、演示或规划中就标为已完成；状态必须能够回到当前代码、自动测试、浏览器验收或长期运行记录。

本文中的用语约定：

- **必须**：对应阶段退出前不可缺少；
- **应当**：默认需要，只有记录理由和替代控制后才能调整；
- **可以**：候选增强，不阻断当前阶段；
- **已实现**：当前产品已有可运行闭环和自动或人工验收证据；
- **部分实现**：已有纵向切片，但覆盖、规模或验收证据尚不充分；
- **未实现**：仍属于目标，不得写成现状。

## 2. 产品定位与用户结果

PLDR 是面向开源情报工作的证据优先工作台。它不以“收集最多文章”或“生成一段看似完整的 AI 答案”为目标，而是帮助分析员围绕一个问题持续完成：

```text
确定关注范围
→ 监测已知来源、发现未知线索、导入已有材料
→ 看见新增、变化、失败和待核对内容
→ 核对原文与候选关系
→ 人工新建、合并、修改或驳回
→ 形成可追溯事件、主张、证据与研判
→ 生成带引用的专题简报
```

用户不应被迫理解数据库表或内部状态机。`Source`、`Document`、`Snapshot`、`Claim`、`Evidence` 等对象用于保证追溯和一致性；面向用户应优先使用“专题、来源、材料、待核对、事件、依据、研判、报告”等任务语言。

“全球军事与安全动态”是 PLDR 的首选业务验证场景之一，而不是产品的唯一边界。它应被实现为可配置专题包；同一产品还应能承载供应链风险、制裁、企业调查或地区态势等公开信息任务。

## 3. 信息进入方式与统一边界

### 3.1 三类并列输入

| 输入方式 | 用户什么时候使用 | 当前边界 |
| --- | --- | --- |
| 已知来源监测 | 已经知道哪个网页、RSS 或 API 值得长期关注 | 固定公共网页和 RSS/Atom 已有切片；通用 API、必要的受控浏览器来源未完成 |
| 动态关键词发现 | 不知道准确 URL，需要围绕地区、实体或事件寻找线索 | Brave Search API 与自管 SearXNG 适配已实现；当前不自动定时重跑关键词 |
| 主动导入 | 手头已有网页、粘贴文本或本地文件 | 网页、文本和受支持文件已实现 |

三类输入必须汇入同一专题的处理和审核闭环。搜索不是其他输入的上游，固定来源也不能绕过人工确认。搜索结果标题、摘要、排名，RSS 提供的摘要以及 AI 候选都不是已经确认的事实。

### 3.2 专题包

一个可运营专题包应当声明：

- 分析问题与使用者；
- 地区、时间、语言和事件类型范围；
- 固定来源目录、来源类型、检查周期和使用条款；
- 动态搜索词、实体词和排除词；
- 重要事件的判断规则及其依据；
- 今日输出和周期报告模板；
- 已知覆盖缺口、不可见范围和人工责任。

专题包只能定义关注范围和采集策略，不能预先决定事实结论。没有冻结来源目录和覆盖边界时，产品不得声称已经覆盖“全世界所有大事”。

## 4. 功能要求

### 4.1 专题与分析员工作流

| 编号 | 功能要求 | P1 验收结果 | 当前状态 |
| --- | --- | --- | --- |
| FR-001 | 系统必须以专题作为搜索、采集、审核、事件和报告的主要工作范围 | 用户能够创建和进入专题；材料、任务、查询历史、合并目标、正式事件和报告默认限定在该专题；范围不可用时不能静默回退到全局 | 已实现 |
| FR-002 | 专题首页必须回答“今天需要处理什么” | 分开显示待核对、处理中、失败、已确认事件和来源故障；空状态、未知和失败保持真实；不得把资讯流或候选数量冒充态势结论 | 部分实现：已有注意力队列，过去 24 小时变化、来源分歧和覆盖缺口仍需收敛 |
| FR-003 | P1 必须形成至少一个可复用的真实专题包 | 专题包包含冻结的 30–50 个来源目录、动态发现规则、输出模板、覆盖边界和验收样本；首选验证“全球军事与安全动态”场景 | 未实现 |
| FR-004 | 技术对象必须通过用户任务语言呈现 | 核心流程不要求用户理解原始 JSON、数据库表或内部状态码；必要技术信息放在详情和诊断区域 | 部分实现：语义预览和中文状态已存在，部分页面仍偏运行记录 |

## 5. 性能、可靠性、安全与易用性指标

### 5.1 P1 参考环境与统计口径

除非某项指标另有说明，P1 性能验收使用以下参考环境：

- Linux x86_64，4 vCPU、8 GiB RAM、SSD；
- Python 3.12，单 API 进程和单 collector；当前切片以 SQLite 记录回归基线，P1 退出还应在路线图选定的正式持久层上重复关键指标；
- 1 名并发分析员；
- 50 个监测来源、5,000 条采集运行、1,000 条待处理材料、500 个事件、2,000 篇文档的验收数据集；
- 浏览器视口为 1440×900 和 390×844；
- 外部搜索、目标网站、DNS 和模型耗时单独记录，不计入本地接口性能，但必须计入用户看到的端到端耗时与失败分类。

任何成功率都必须同时报告分母、样本类型、时间窗口、排除项和失败分类。不能删除失败样本后只报告成功数据，也不能用演示数据代替真实来源运行。

### 5.2 指标矩阵

| 编号 | 指标要求 | P1 目标与验收方法 | 当前状态 |
| --- | --- | --- | --- |
| NFR-001 | 人工确认边界 | 受控负向测试中，未处理、处理中、失败、撤销、驳回、删除和重复操作造成的正式对象新增或修改数必须为 0 | 已实现并有自动测试 |
| NFR-002 | 证据可追溯率 | P1 真实专题验收样本中，100% 已确认主张可回到精确证据片段、快照、文档和来源；无法回链即为失败 | 自动契约已实现；真实专题样本未完成 |
| NFR-003 | 证据定位正确性 | 所有候选和正式 Evidence 都必须精确命中其绑定快照；不允许用搜索摘要或 RSS 摘要冒充已抓取原页 | 已实现；RSS 原页追抓仍未完成 |
| NFR-004 | 真实来源规模与持续运行 | 冻结的 30–50 个来源连续运行 72 小时；公布总运行数、成功数、未变、变化、重复、无效、失败、重试和恢复，不允许只给“系统正常”的主观结论 | 未验收 |
| NFR-005 | 调度及时性 | 在参考环境和正常维护窗口外，至少 95% 到期运行应在 `max(5 分钟, 配置周期的 10%)` 内开始；暂停和上游停机必须单列 | 未验收 |
| NFR-006 | 崩溃恢复 | 受控故障注入中任务丢失数为 0、同一版本或 RSS 条目重复入箱数为 0；恢复应在租约到期后两个轮询周期内重新进入可执行状态 | 单次崩溃和租约重放已有自动测试；72 小时与连续双故障未验证 |
| NFR-007 | RSS 目标内去重 | 同一目标重复返回完全相同条目时新增 Intake 数为 0；内容变化按新材料处理；跨目标重复不冒充已自动解决 | 已实现并有自动测试 |
| NFR-008 | 失败隔离与终态可见 | 受控批量中每项都必须到达可解释状态；一项失败导致的其他项目丢失数为 0；重启或刷新后状态与服务端一致 | 已实现当前切片；真实长期运行未验证 |
| NFR-009 | 有界抓取 | 默认正文上限 5 MiB；请求、重定向和流读取总墙钟上限 30 秒；超限、非文本和压缩风险必须明确拒绝。P1 退出前还必须给 DNS 阶段设置可验证上限 | 部分实现：正文和异步请求阶段有界，极端同步 DNS 卡顿仍是已知风险 |
| NFR-010 | SSRF 与默认拒绝 | 私网、回环、链路本地、保留地址、带凭据 URL、非 HTTP(S)、不安全重定向及解析不确定样本必须 100% 拒绝且不产生正式对象；P1 退出前应关闭校验与实际连接之间可利用的 DNS 变化窗口，或记录等效网络层控制 | 部分实现：字面地址、解析和逐跳重定向已有防护；DNS 变化窗口仍需收敛 |
| NFR-011 | 搜索批量边界 | 单查询最多保留 100 条去重结果，单批最多选择 100 条；应增加 100 条边界自动测试，确保没有静默截断、重复或整批失败 | 实现上限已存在；自动测试当前覆盖 25 条，边界证据不足 |
| NFR-012 | 本地交互性能 | 参考数据集下，不访问外部网络的专题首页、今日队列、事件档案和来源详情 API 的 p95 应不超过 1 秒；对应页面从操作到主要内容稳定显示的 p95 应不超过 2 秒 | 尚未建立基准测试 |
| NFR-013 | 响应式可用性 | 两种参考视口均能完成“创建专题—发现/导入—查看进度—审核—确认—打开事件—生成报告”；正文无横向溢出，关键动作无需依赖仅悬停可见内容 | 已有受控浏览器记录；新候选仍须按受影响页面复验 |
| NFR-014 | 错误可理解性 | 验收矩阵中的 100% 受控失败场景必须显示用户可理解的原因、影响、重试语义和下一步；不能只显示“系统错误”或提供违反安全策略的重试按钮 | 部分实现，需完成全入口清单验收 |
| NFR-015 | 增量迁移兼容 | 从每个受支持旧版本数据库升级时，业务行数和对象关联不减少；新增列、表和索引可重复执行；半迁移能修复；完整测试重复运行后结果一致 | 已实现当前 SQLite 增量迁移并有自动测试；正式迁移工具未完成 |
| NFR-016 | 模型用量与成本 | 每次模型任务记录任务类型、供应商、模型、耗时、成功/降级、输入输出用量和可计算成本；专题和时间窗口可汇总 | 未实现 |
| NFR-017 | 密钥与公网边界 | 密钥只能来自运行环境或受控秘密存储且不得出现在日志、数据库和前端；公网开放时必须由认证网关或统一身份层保护，CORS 不得被描述为认证 | 部分实现：环境变量与部署说明已有；应用级角色权限属于 P3 |
| NFR-018 | 正式持久层与迁移 | 按路线图完成 PostgreSQL/PostGIS 与正式迁移路径；从受支持 SQLite 数据迁移后，业务对象、关系、快照、处置记录和引用数量不减少；迁移失败可从备份恢复，且同一迁移不可重复写入对象 | 未实现：当前只有 SQLite 增量迁移和单 collector 边界 |

## 6. P1 阶段退出条件

P1 只有在下列结果同时成立时才能退出：

1. `FR-001` 至 `FR-004` 的用户主线成立，至少一个真实专题包能够让分析员完成“今天发生什么、依据是什么、还缺什么”的任务；
2. 三类输入保持并列，主动导入、关键词发现、固定网页、RSS、通用 API 和真实专题必要的受控浏览器来源进入同一持久处理链；
3. `FR-201` 至 `FR-205` 的人工确认边界没有被自动化绕过；
4. `NFR-004` 的 30–50 个来源、72 小时运行报告完成，并满足调度、恢复、去重和失败隔离指标；
5. `NFR-009`、`NFR-010` 的抓取边界与 SSRF 风险达到 P1 要求；
6. `NFR-012` 建立可重复性能基准，核心页面和本地接口达到目标；
7. `NFR-016` 的模型用量和成本能够追踪；
8. `NFR-018` 的正式持久层、迁移和恢复验证通过；
9. 真实专题抽样中的已确认主张满足 100% 证据回链；
10. 自动测试、Compose 配置、桌面/窄屏浏览器流程和验收报告均基于同一候选代码树。

GitHub CI 通过只能证明自动检查通过，不能单独代替真实来源、长期运行、浏览器任务或用户验收。旧截图、旧分支测试、演示数据量和搜索引擎某次返回条数也不能作为新候选的退出证据。

## 7. 后续阶段边界

| 阶段 | 主要结果 | 本阶段不提前声称 |
| --- | --- | --- |
| P2 | 一个分析团队在真实专题中连续工作，完成任务分派、双人复核、提醒、实体别名和报告审核 | 企业级权限、不可抵赖审计、稳定开放平台 |
| P3 | 形成可治理、可集成、可恢复的平台，具备角色权限、审批、正式迁移、API/MCP、备份恢复和服务指标 | 自动事实裁决、预测或无人控制的外部动作 |
| P4 | 在冻结评估集上验证跨语言早期信号、冲突主张、传播链、来源独立性和受控情景推演 | 把推断或预测包装成事实 |

## 8. 当前明确不做

- 不建设无边界的全网爬虫，也不承诺覆盖全世界所有公开信息；
- 不把新闻聚合、搜索排名或模型摘要直接升级为正式证据；
- 不自动确认事件、自动事实裁决或无人审核发布报告；
- 不在 P1 引入团队审批、企业级权限、复杂插件生态、通用图数据库或预测系统；
- 不为追求功能数量机械复制参考项目；任何代码、服务或数据源接入都必须单独固定版本并核对许可证、版权、部署和数据条款；
- 不把 Windows 展示端、某个模型供应商或某个 Agent 工具固定为产品架构前提。

## 9. 验收证据与变更规则

每项要求的验收记录至少包含：候选提交、测试环境、数据或来源样本、执行时间、命令或用户任务、实际结果、失败与限制。性能报告必须保留原始计数和统计口径。

要求发生变化时必须同时更新本文档、`ROADMAP.md` 和受影响切片文档；不得只修改状态词而不提供新证据。降低指标、扩大自动化权限、改变人工确认边界、扩大公网访问或引入许可证风险，均属于需要重新确认的实质变化。

当前项目原生自动验证入口为：

```bash
./scripts/test-p0.sh
docker compose config --quiet
git diff --check
```

真实来源运行、浏览器用户任务、安全负向场景和性能基准需要单独记录，不能用上述命令的成功替代。
